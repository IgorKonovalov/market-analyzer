# ADR-0002 — UI ↔ sidecar IPC over localhost HTTP

> **Status:** accepted
> **Date:** 2026-05-17
> **Related plan(s):** [0001-bootstrap](../plans/0001-bootstrap.md)
> **Related ADRs:** [ADR-0005](0005-desktop-shell-electron.md), [ADR-0008](0008-electron-shell-conventions.md)

## Context

The desktop shell (Electron, per [ADR-0005](0005-desktop-shell-electron.md)) needs to call into the Python sidecar to fetch market data, eventually run backtests, and persist user state. The transport is a decision because both ends have to agree forever, and changing it later costs us every existing endpoint.

The two realistic options are:

1. **Local HTTP** — sidecar runs `uvicorn` on `127.0.0.1:<auto-port>`, the renderer does `fetch()`.
2. **Stdio JSON-RPC** — the Electron main process spawns the sidecar, talks to it over the child process's stdin/stdout using a JSON-RPC framing, and forwards calls into the renderer via `contextBridge`.

Forces:

- **Request volume is low.** Week-one polling is one request per user interaction. Even at "running ten backtests in parallel" later, we're talking dozens of requests per second, not thousands. Transport perf is not a real constraint.
- **Debuggability is high-value for a solo developer.** Being able to `curl -H "Authorization: Bearer <secret>" http://127.0.0.1:<port>/ohlcv` while the UI runs makes every "is it the UI or the sidecar?" question a 10-second answer.
- **The Python ecosystem favors HTTP servers.** FastAPI + pydantic gives us schema validation, OpenAPI docs (which the renderer's typegen consumes), and an async story for almost no work. The stdio JSON-RPC ecosystem in Python is thinner — `jsonrpcserver` or hand-rolled.
- **Port conflicts are a real but small annoyance.** Mitigated by letting the OS pick a free ephemeral port at startup and forwarding it from the Electron main process to the renderer via the preload bridge, rather than hard-coding 8000.
- **Security.** Binding to `127.0.0.1` only (not `0.0.0.0`) means no other machine on the LAN can talk to the sidecar. Other local processes on the same machine *can*, however, reach an open localhost port — so the sidecar enforces a **per-launch bearer-token shared secret** on every non-`/healthz` request. The secret is generated by the Electron main process at spawn time, passed to the sidecar via `argv` (`--secret=<hex>`), and forwarded to the renderer via the preload bridge. It is never persisted to disk and never logged.

## Decision

We will use **localhost HTTP** between the Electron renderer and the Python sidecar. The sidecar binds to `127.0.0.1` on a port chosen at startup (passing `port=0` to uvicorn, then reading back the actual port from the socket) and prints `PORT=<n>` to stdout. The Electron main process captures this line and exposes `{ port, secretToken }` to the renderer via the `sidecar:get-port` preload bridge (per [ADR-0008](0008-electron-shell-conventions.md)).

Every request to the sidecar except `GET /healthz` must carry `Authorization: Bearer <secret>`; the auth middleware rejects requests without it with 401. The secret is a fresh 32-byte hex string generated per launch by the main process; the sidecar reads it from `argv[--secret=...]` on startup. Requests that fail auth never reach route handlers.

Endpoints are RESTful and return JSON validated against pydantic models in `src/market_analyser/data/types.py` (and other domain modules as they land). We do not adopt JSON-RPC framing on top of HTTP — plain REST is enough for our needs and matches what FastAPI gives us natively. CORS is *not* enabled — the renderer loads from a file:// origin (in production) or `http://localhost:5173` (Vite dev) and reaches the sidecar through `fetch` to `http://127.0.0.1:<port>`; the sidecar's CSP-relaxation in the renderer is handled by [ADR-0008](0008-electron-shell-conventions.md)'s `connect-src http://127.0.0.1:*` line, not by server-side CORS.

## Consequences

### Positive
- `curl` and the browser's DevTools network panel work out of the box. This is the single biggest debugging dividend.
- FastAPI + pydantic gives us validation, OpenAPI docs at `/docs`, and async migration path for free.
- Schema generation for TS types is a solved problem (`datamodel-code-generator` or `openapi-typescript`).
- Postman / IDE HTTP clients work for manual testing.
- If we ever need a headless mode ("run a backtest from CLI without the UI"), it's a one-line `httpx` script — no sidecar refactor.

### Negative
- **Port-pick complexity.** Hard-coding port 8000 is simpler but conflicts with anything else the user runs. The auto-port + stdout-capture pattern is more code in `desktop/electron/main.ts` and in `src/market_analyser/api/__main__.py`. Worth it.
- **HTTP overhead per call.** Roughly 1–2 ms vs. stdio's <0.1 ms. Invisible at our request rate; would matter at >10k req/s, which is not a regime we're heading into.
- **Localhost firewalls on Windows can prompt on first launch.** Binding to `127.0.0.1` (not `0.0.0.0`) avoids the inbound-rule prompt on most setups but not all. If users see the prompt, we document it.
- **Two-process model means we have to manage sidecar lifecycle explicitly.** The Electron main process must spawn the child, wait for `/healthz` before showing the window, restart once on crash, and kill the child on `before-quit`. Stdio would give us cleanup implicitly. See Plan 0001 phase 4 for the supervisor implementation.
- **Shared-secret in argv is visible in process listings.** A second local user on the same machine can read `argv` of the sidecar process and recover the bearer secret. The threat model accepts this for a single-user desktop app; if multi-user-host becomes a concern, switch to env-var injection at spawn (captured as a followup in Plan 0001).

### Neutral
- Streaming responses (e.g. backtest progress) need SSE or WebSockets over HTTP, which is fine in FastAPI but is a bit more code than streaming over stdio. Deferred until a backtest plan needs it.

## Alternatives considered

### Alternative A — Stdio JSON-RPC
Faster, no port conflicts, lifecycle tied to the parent process. Rejected because **debuggability matters more than the perf difference at our scale**. With stdio, every "is the sidecar even alive?" check requires building a test harness; with HTTP, it's `curl /health`. The author works solo and triages many issues a day — the cumulative time saved is large.

### Alternative B — Embed Python in the renderer / main process (e.g. PyO3 in a Rust shell or pythonia in Node)
Theoretically the cleanest: one process, no IPC. Rejected because it forces us to embed Python in the shell binary (or vice versa), couples our Python release cycle to the shell, and breaks the clean process boundary the architecture relies on for testing and for the planned headless mode. The "data layer is its own process" property is structurally valuable and survived the Tauri→Electron shell change unchanged.

### Alternative C — Unix domain sockets / Windows named pipes
A middle ground: faster than HTTP, no port conflicts, but still socket-based so `curl` users can hit it via `--unix-socket`. Rejected because cross-platform handling (Windows named pipes have different semantics from Unix sockets) is more code than just picking an ephemeral TCP port, for a perf win we don't need.

## Notes

- The chosen-port pattern: pass `port=0` when constructing the uvicorn `Server`, then read `server.servers[0].sockets[0].getsockname()[1]` after `await server.serve()` starts. Print to stdout as a single line `PORT=<n>` before anything else logs. The shell side: the Electron main process reads child stdout line-by-line, matches `^PORT=(\d+)$`, stores `{ port, secretToken }` for the preload bridge, then waits for `GET /healthz` to return 200 (max 10 s) before calling `BrowserWindow.show()`.
- The health endpoint is `GET /healthz` (per Plan 0001 phase 1), not `/health`. It is the only route exempt from bearer-token auth so the supervisor can probe sidecar liveness without holding the secret on its supervisory path.
- If `/healthz` is unreachable for >10 s after spawn, the Electron main process shows a fatal-error window with a "view logs" button. Detailed in Plan 0001 phase 4.
- **History.** This ADR was originally framed against Tauri (per the superseded [ADR-0001](0001-tauri-vs-electron.md)). It was rewritten on 2026-05-17 to reflect the Electron decision in [ADR-0005](0005-desktop-shell-electron.md) and the bearer-token requirement from [ADR-0008](0008-electron-shell-conventions.md). The transport decision (localhost HTTP) is unchanged; only the shell-specific framing and the auth requirement were updated. No code had been written against the earlier text.
